# v0.5.1

## 修正:送往裝置的多片段指令改為節流發送

Backend 下發的指令若超過一個 ESP-NOW 封包(250 B),Hub 會把它切成多個片段。在此版本之前,
`EspNowCommandDispatcher` 是在一個緊密迴圈裡把所有片段連續 `esp_now_send()` 出去 —— 這正是
這條鏈路上已經三度造成片段遺失的模式:radio 佇列溢出,裝置端的重組器等不到缺口而逾時,
一個大指令就**無聲地**永遠送不到。

App 安裝(`file_write_chunk` 帶 hex 資料)讓這種大指令變成常態,所以現在修。

- 片段改由節流狀態機送出,分散在與裝置端相同的 15 ms 發送視窗內。
- 同一時間只排空一個 burst。另一台裝置的指令若在 burst 尚未送完時到達,會**延後**而不是
  覆寫正在送的片段;延後的指令會在下一次 `service()` 立即送出,且不計入重送次數。
- 重送同樣會等 radio 空閒。

## 實機驗證

GCU V2.3.D Hub + v1.5.F 裝置(韌體 v1.2.1),Backend 為本機測試實例:

- 經由 Hub 安裝 app 套件,請求大小約 280 B / 890 B / 1690 B(2 / 4 / 8 個片段),
  裝置端每一次 sha256 驗證皆通過;往返時間 111–568 ms。
- 3237 B 的 `sysmon` 以 96 B chunk 安裝約 7 s,以 800 B chunk 約 1.6 s。
- 四個 flow 槽正常執行,`app_events`(含 `frame_seq`)經 Hub 正確回傳。

**未驗證**:兩台裝置同時收到多片段指令(延後而不覆寫的那條路徑)—— 需要第二台裝置。

## 相容性

- 不改變 ESP-NOW 或 uplink 的線路格式,對已配對裝置與 Backend 無相容性影響。
- 每台裝置同時只能有一個指令在途(`device_command_already_in_flight`)的行為不變,與 Gateway 一致。
