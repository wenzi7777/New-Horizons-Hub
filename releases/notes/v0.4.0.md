# v0.4.0

## Changes

### Fix: ESP-NOW control commands could fail entirely, and the device's LED blinked repeatedly for a single command

Real-hardware debugging (concurrent Hub+device serial capture while sending a
live `status` command) found the Hub's `EspNowCommandDispatcher` resending
the raw command every 500ms for up to 30 attempts (~15s) without ever
accepting a reply, even though the device answered correctly on every single
attempt. Fixed with a new ack-before-execute step on the ESP-NOW control
channel, mirroring the UDP/Gateway path's existing ack-first design:

- The device now sends a one-byte ack (`0xE7`) the instant a command frame
  finishes reassembling, before it even starts processing it.
- `EspNowCommandDispatcher` stops resending the raw command the moment it
  sees that ack, and switches to a separate, longer deadline (10s) for the
  (possibly slow) response instead of continuing the pre-ack 500ms resend
  loop.

This also fixes the repeated-LED-blink symptom, since the device no longer
reprocesses (and re-signals) the same command on every blind resend.

Verified on real hardware: a `status` command that previously failed with
`command_delivery_timeout` after 29+ resends now succeeds on the first
attempt, with no extra LED events.

## Also in this release

- Pairs with `NewHorizonsOS-OTA` v0.15.0, which implements the device side
  of the new control-ack protocol and additionally pauses its own sensor
  streaming during a pending command to remove ESP-NOW airtime contention
  with the command response.
