# v0.3.0

## Changes

### Fix: a paired device that migrated to a different Hub kept being falsely reported as still connected here

- The device-slot roster never expired a paired device -- once this Hub
  ever paired a device, it kept reporting it `connected: true` in every
  ~5s `gateway_status` heartbeat forever, even long after the device
  moved to a different Hub. With two Hubs both truthfully-per-their-own-stale-bookkeeping
  claiming the same device, the Desktop app's display of "which
  gateway/hub serves this device" would flip between them.
- A device slot is now actively reaped (freed, including the ESP-NOW peer
  table entry) once it's been silent for 30s. This also fixes a real
  capacity leak -- a Hub that had ever seen 4 devices (even long-gone
  ones) would refuse a genuinely-present 5th; freed slots are available
  again.

### New: distinct LED signal for New Horizons Direct pairing

- Added `LedSignal::EspNowConnecting` (mirrors `NewHorizonsOS-OTA`'s
  identical addition) -- same color/pattern as the existing
  `WifiConnecting`, kept as its own shared-enum value rather than reused,
  following this project's existing precedent (`UplinkDegraded` is
  Hub-only but still lives in the same shared, hand-mirrored enum). This
  Hub firmware doesn't construct it directly, but keeps its copy of
  `LedController.h`/`.cpp` byte-identical to the device repo's, as
  established.

## Also in this release

- Pairs with `NewHorizonsOS-OTA` v0.14.0, which uses the new LED signal
  and adds its own fixes for pairing-timeout fallback and pausing sensor
  streaming during an active OTA relay.
