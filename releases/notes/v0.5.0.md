# v0.5.0

## 新增:BQ25180 充電器設定

GCU V2.3.D 板上有 BQ25180 充電 IC(`NHOS_BOARD_HAS_BQ25180 1`),但在此版本之前 Hub 韌體完全沒有碰它 —— 整個韌體連一次 `Wire.begin()` 都沒有,`NHOS_BOARD_HAS_BQ25180` 這個旗標在 `BoardConfig.h` 之外從未被引用。

BQ25180 本來就會依暫存器預設值自行充電,所以這個版本**不是**「讓 Hub 開始充電」,而是讓它**依照我們的設定**充電,而不是晶片的出廠預設值:

- VBAT 上限 4.2 V、依 profile 設定 ICHG 充電電流、輸入電流上限 500 mA、安全計時器
- 預設 profile 為 `slow`(200 mA),與裝置韌體同一個 `charge_profile` NVS key、同一個預設值
- 每個寫入的暫存器都會讀回驗證

由 `NewHorizonsOS-OTA` 同步過來的 `PowerManager.h/.cpp` 與 `PowerStatusJson.h/.cpp`(逐字複製,已加入 README 的 manual-sync 清單)。

### 實作細節

- 充電器在 `setup()` 中於**兩個 early return 之前**就啟動(quick-boot factory reset、以及「尚未設定 Wi-Fi」的 portal 模式)。使用者在設定入口前操作時,正是 Hub 最可能插著 USB 的時候,那時也必須要能充電。
- `power.service(millis())` 在 `loop()` 的**兩條路徑都無條件呼叫**,沒有包在額外的計時器裡。`PowerManager::service()` 內部已自行節流到 1 Hz,而那個 1 Hz 的 STAT0 讀取同時也是在餵 BQ25180 的 I2C watchdog —— 若改用較慢的外層計時器,watchdog 逾時會讓晶片把暫存器還原成預設值,充電電流會無聲地掉回出廠值。

### 已知限制

- **沒有電量顯示。** V2.3.D 沒有 MAX17048 電量計(`HAS_MAX17048` 為 0),板上也沒有電池分壓 ADC 通道,BQ25180 本身不提供 VBAT/SoC 讀值。Hub 能得知的只有三態充電狀態加上 VIN 是否存在。因此 `BatteryGaugeManager` 及整套 battery profile/LED policy 都**沒有**移植過來 —— 在這塊板子上它們全是死碼。
- **狀態 LED 不顯示充電狀態。** 沒有電量計就無法區分「充電中」與「沒裝電池」(這正是 `ChargeState::ChargingOrMissing` 命名的原因),而 Hub 是常插電的中繼器、多數情況根本沒裝電池 —— 若讓 LED 反映充電狀態,最常見的情境會變成永久亮琥珀色而不是 Online。這顆單一像素維持只表示連線狀態。
- **充電狀態不會回報給 Desktop。** `gateway_status` payload 未新增欄位;backend 的 `record_gateway_summary()` 是白名單複製,Desktop 也還沒有 Hub 電池的 UI。要做需要 Hub payload、backend 白名單、frontend 三層一起改。

## 相容性

- 僅影響 Hub 自身硬體,不涉及 ESP-NOW 或 uplink 線路格式,對已配對裝置與 Backend 無相容性影響。
