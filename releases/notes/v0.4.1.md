# v0.4.1

## Changes

### Pause sensor-data relay to the backend while a control command is pending

Real-hardware debugging of persistent `command_delivery_timeout` failures found `onHubFrameReady()` calling `HubUplinkClient::sendSensorPacket()` synchronously, on the Hub's single Arduino task, up to ~55-60 times/sec under normal streaming -- and that call is a **blocking** TLS WebSocket send over the internet. Every one of those blocking sends stalls the entire `loop()` iteration, delaying `EspNowCommandDispatcher::service()`'s resend timing and `EspNowHubManager`'s own ESP-NOW receive processing right when a control-command ack/response needs to be handled promptly.

The Hub now skips forwarding a sensor-data frame (dropping it -- sensor data is lossy by design) while `EspNowCommandDispatcher::hasPendingCommand()` is true, removing this specific source of main-loop stalling during a command exchange.

## Known issue, not resolved by this release

This fix is verified correct and beneficial on its own, but real-hardware testing found it does **not**, by itself, fully eliminate `command_delivery_timeout` -- the failure still occurs intermittently under conditions that didn't isolate cleanly to a single cause even after extensive live debugging. See the paired `NewHorizonsOS-OTA` v0.15.1 release notes for what else was tried (including two more invasive fixes -- pausing the Hub's own ESP-NOW poll cycle, and aborting an in-flight device-side data burst -- that were built, tested, and reverted after they didn't measurably help). Testing suggests real-world WiFi/RF conditions may be a factor. If this persists, further diagnosis will use the new ESP-NOW send-status callback added on the device side in v0.15.1.
