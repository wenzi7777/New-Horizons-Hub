# v0.4.2

## Fixed: `status` commands to New Horizons Direct devices always timed out

Hub-side half of the fix described in `NewHorizonsOS-OTA` v0.15.2 (read that
release note for the full root-cause analysis). The device's `status`
response had grown to ~5200 bytes, past the ESP-NOW frame format's
`16 * 240 = 3840` byte limit, so the device silently sent nothing and the
Hub reported `command_delivery_timeout`.

- Fragment budget raised to **32 fragments (7680 bytes)** so the Hub can
  reassemble the larger control responses. Data and OTA paths stay pinned to
  the original 16-fragment budget, keeping the OTA chunk size byte-for-byte
  unchanged.
- Fixed the same `(1u << 32)` undefined behaviour in the shared reassembler
  (it would report a 32-fragment frame complete on its first fragment).
- Control-frame reassembly scratch is now **shared across device slots**
  instead of one 7680B buffer per slot. This class already reassembles at
  most one control frame at a time (there is a single global
  `controlFrameReady_`/`controlFrameBuffer_` slot), so this is consistent
  with the existing design -- and it matters: a per-slot copy pushed RAM up
  ~31KB, which real-hardware testing showed was enough to make the Hub's TLS
  handshake fail with `RSA ... BIGNUM - Memory allocation failed` and drop
  its backend uplink entirely. RAM is back to ~baseline (34%).
- `EspNowCommandDispatcher::sendFragmentsTo()` now logs instead of silently
  sending nothing if a command payload can't be fragmented, and its fragment
  array moved off the stack (it would otherwise be ~8KB of stack).

## Also in this release

- Requires `NewHorizonsOS-OTA` v0.15.2 on paired devices -- both sides carry
  the matching wire-format change.
